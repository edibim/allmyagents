# AllMyAgents — Agent Integrations

AllMyAgents computes one **Effective Developer Context** — your Developer
Profile, optionally overridden for the current project (`allmyagents
context`) — and hands it to whichever AI coding agent you actually use.
`allmyagents init-project` configures every agent below for the current
project in one run, each through its own adapter (`internal/adapters`).
None of them share generated files or duplicate profile logic; they all
render from the same `context.Build`/`Render` core.

## Status labels used below

- **Verified** — the exact mechanism was exercised end-to-end in this
  repository's automated tests, including a real subprocess run where
  applicable, against the agent's currently published documentation.
- **Supported, configuration-verified** — the generated file/config is
  fully tested (content, idempotency, tracked-file safety), but a live,
  fresh session of the agent itself was not run to confirm it picks the
  context up. This is not the same as "verified" — see each section's
  manual verification steps to confirm it yourself.
- **Experimental** — supported-but-unverified, with an extra caveat:
  either the agent's own documentation is thin/ambiguous, or third-party
  sources disagree with it.

## The shared safety rule

Every adapter that manages a working-tree file follows the same
never-overwrite rule, applied in this order:

1. **Already tracked by git** → skip. Several of these mechanisms
   (`AGENTS.md`, `.github/copilot-instructions.md`, Antigravity's rule
   files) are also the conventional home for a project's real,
   team-shared instructions; if that file already exists and is
   committed, AllMyAgents leaves it alone.
2. **Exists, untracked, but wasn't generated by AllMyAgents** → also skip.
   Being untracked doesn't mean a file is safe to overwrite — it might be
   a draft you haven't committed yet, something another tool manages, or
   a symlink. AllMyAgents only ever overwrites a file it can identify as
   its own, via the marker comment described below.
3. **Exists and carries AllMyAgents' own marker** → safe to regenerate.
4. **Doesn't exist yet** → create it.

In every case where AllMyAgents does *not* touch the file, it reports
`skipped` with the specific reason, never silently. Every file it does
create or regenerate opens with an HTML comment identifying it as
AllMyAgents-generated, personal, local-only content.

**Git exclusion is reported honestly, not assumed.** After writing a file,
AllMyAgents only claims "git-excluded, local only" when it actually found
a real Git repository and added the path to `.git/info/exclude` (never
`.gitignore`, which stays untouched). If there is no Git repository yet —
or the layout is a worktree/submodule, which this version doesn't attempt
to manage exclusions for — the file is still created (agents need it to
work at all), but the reported detail says so plainly: something like *"no
git repository found here yet — this file is not automatically protected
if you run `git init`/`git add` later."* If you see that message, and you
do plan to initialize Git in that directory, add the file to `.gitignore`
yourself first, or re-run `allmyagents init-project` after `git init` so
AllMyAgents can protect it going forward.

## Claude Code

**Status: Verified.**

**Mechanism:** Claude Code's documented [memory
system](https://code.claude.com/docs/en/memory) reads `CLAUDE.md`, not
`AGENTS.md`, but its official, general-purpose local-context mechanism is
a **hook**: a shell command Claude Code runs itself and whose stdout it
injects into the session. AllMyAgents uses a `SessionStart` hook running
`allmyagents context --session-start-hook`, which prints the current
Effective Developer Context wrapped in Claude Code's documented
`hookSpecificOutput.additionalContext` JSON shape. Unlike every other
agent here, nothing is ever frozen into a static file — Claude Code always
gets a freshly computed context at the start of each session.

**Generated files:** `.claude/settings.local.json` (adds a `SessionStart`
hook entry; preserves any other settings/hooks already there).

**Setup:** `allmyagents init-project` (no extra steps).

**Verification:**
- Run `allmyagents init-project`, then open a new Claude Code session in
  the project and run `/context` — `.claude/settings.local.json` should
  be listed, and Claude should be able to answer questions about how you
  like to work (autonomy, review style, etc.) without you explaining it.
- This repository's test suite includes a real subprocess test
  (`internal/cli/acceptance_test.go`) that builds the actual
  `allmyagents` binary and runs the literal hook command Claude Code
  would run, asserting the JSON matches the documented schema — the
  closest thing to a live acceptance test achievable without a running
  Claude Code installation.

**Limitations:** none known; this is the most mature integration here
since AllMyAgents' own development uses it.

## Codex CLI

**Status: Supported, configuration-verified.**

**Mechanism:** Codex CLI auto-discovers an [`AGENTS.md`
file](https://developers.openai.com/codex/guides/agents-md) at the
repository root with no configuration required. Codex has no dynamic hook
system, so AllMyAgents writes a static `AGENTS.md` carrying the current
Effective Developer Context — but only when that path isn't already
tracked by git (see "The shared safety rule" above), since `AGENTS.md` is
also the conventional home for a team's real, shared project
instructions.

**Generated files:** `AGENTS.md` (repository root) — only if it's absent,
untracked-and-AllMyAgents-generated already, or doesn't exist yet (see "The
shared safety rule" above); git-excluded only when a real Git repository
is found.

**Setup:** `allmyagents init-project`.

**Verification:**
- Run `allmyagents init-project`, confirm `AGENTS.md` was created (or, if
  your project already has a real tracked `AGENTS.md`, confirm the
  command reported `codex: skipped` and that your file was untouched).
- Open Codex CLI in the project and ask something like "what do you know
  about how I like to work?" — it should reflect your Developer Profile.

**Limitations:** this sandbox's shell environment permanently blocks
invoking the `codex` binary and has no OpenAI account configured, so a
live fresh-session run could not be executed here. Only file
generation/content/safety behavior is automatically tested.

## GitHub Copilot (VS Code)

**Status: Supported, configuration-verified.**

**Mechanism:** VS Code auto-discovers [`.github/copilot-instructions.md`
at the workspace
root](https://code.visualstudio.com/docs/agent-customization/custom-instructions)
with no settings required — the stable, original repository-instructions
mechanism (VS Code's newer `AGENTS.md` support requires an experimental
setting, so this integration deliberately doesn't depend on it). As with
Codex, `.github/copilot-instructions.md` is conventionally a team's real,
committed file, so AllMyAgents only manages it when it isn't already
tracked.

**Generated files:** `.github/copilot-instructions.md` — subject to "The
shared safety rule" above; git-excluded only when a real Git repository is
found.

**Setup:** `allmyagents init-project`.

**Verification:**
- Run `allmyagents init-project`, confirm the file was created (or
  skipped, if your project already has a real tracked one).
- Open the project in VS Code with GitHub Copilot Chat enabled and ask it
  about your working preferences — it should already know them.

**Limitations:** this sandbox has no VS Code / GUI available, so no live
fresh Copilot Chat session could be run here. Only file
generation/content/safety behavior is automatically tested.

## Gemini CLI

**Status: Supported, configuration-verified.**

**Mechanism:** Gemini CLI reads a hierarchical [`GEMINI.md`
file](https://geminicli.com/docs/cli/gemini-md/) by default, but the
filename(s) it searches for are configurable via the documented
`context.fileName` setting in `.gemini/settings.json` (accepts an array).
Rather than writing into `GEMINI.md` itself — the conventional home for a
team's real, shared context — AllMyAgents adds its own distinct filename,
`GEMINI.local.md`, to that search list and writes the Effective Developer
Context there instead. Both the settings merge and the content file
follow the shared safety rule: if either path is already tracked, the
whole integration is skipped rather than partially configured.

**Generated files:** `.gemini/settings.json` (merges `GEMINI.local.md`
into `context.fileName`, preserving any other names/keys already there)
and `GEMINI.local.md` (repository root) — subject to "The shared safety
rule" above for both paths; git-excluded only when a real Git repository
is found.

**Setup:** `allmyagents init-project`.

**Verification:**
- Run `allmyagents init-project`, then check `.gemini/settings.json`
  lists `GEMINI.local.md` under `context.fileName`.
- Open Gemini CLI in the project and run `/memory show` — the
  concatenated context should include `GEMINI.local.md`'s content.

**Limitations:** Gemini CLI isn't installed in this sandbox (it can be
added with `npm install -g @google/gemini-cli`) and would need a Google
account/API key to run a live session, so no live fresh-session run was
attempted here. Only file generation/content/safety behavior is
automatically tested.

## Google Antigravity

**Status: Experimental.**

**Mechanism:** Antigravity's own documentation
(`antigravity.google/docs/rules-workflows/`) describes workspace **Rules**
living under `.agents/rules/` (with `.agent/rules/` kept as a legacy
fallback) as its repository-level context mechanism — a Markdown file with
frontmatter selecting an activation mode (Manual / Always On / Model
Decision / Glob-based). **This is not `AGENTS.md`**, despite several
third-party guides claiming otherwise; this integration follows
Antigravity's own docs rather than those claims. AllMyAgents writes an
"Always On" rule so it's always active for the workspace.

**Generated files:** `.agents/rules/allmyagents-context.md` — subject to
"The shared safety rule" above; git-excluded only when a real Git
repository is found.

**Setup:** `allmyagents init-project`.

**Verification:**
- Run `allmyagents init-project`, then open the project in Antigravity
  and check its Rules view — the AllMyAgents rule should be listed and
  active.
- **Important:** confirm the frontmatter key AllMyAgents used
  (`trigger: always_on`) actually matches what Antigravity's Rules UI
  expects. Antigravity's documentation is a single page and doesn't spell
  out the frontmatter schema in as much detail as the other agents here,
  so this was implemented from the best available description, not a
  full schema reference.

**Limitations:** this sandbox has no GUI and Antigravity itself isn't
installable here (it's a desktop IDE), so no live session was run and the
exact frontmatter schema could not be cross-checked against the product
itself. Treat this integration as a reasonable best effort pending your
own confirmation, not a settled mechanism.
